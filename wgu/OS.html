UNIX STREAMS
A full-duplex I/O interface for character device drivers in UNIX System V
What is STREAMS?

STREAMS is a UNIX kernel framework that provides a standard, modular way to implement character-device I/O and network protocols. It creates a full-duplex communication channel between a user-space process and a device driver, with optional processing modules stacked in between.

Key Insight
A STREAM is like a pipeline of data transformers — raw data enters one end, gets processed by each module in sequence, and exits the other end transformed. Unlike a pipe (one-way), STREAMS are full-duplex (data flows both ways simultaneously).
The 3-Part Architecture
User Space ┌─────────────────────────────────────────┐ │ User Process (app) │ │ read() / write() / ioctl() │ └──────────────────┬──────────────────────┘ │ ┌──────────────────▼──────────────────────┐ ← STREAM HEAD │ Stream Head (sth) │ Interface between user & kernel │ Manages user ↔ kernel boundary │ Handles read/write system calls └──────────────────┬──────────────────────┘ │ ┌──────────────────▼──────────────────────┐ ← MODULE (optional, stackable) │ Module (e.g., TTY) │ Transforms data in both directions │ push() / pop() to add/remove │ Example: encryption, protocol layer └──────────────────┬──────────────────────┘ │ ┌──────────────────▼──────────────────────┐ ← STREAM DRIVER │ Stream Driver │ Actual hardware interface │ Communicates with the device │ Bottom of the stream └─────────────────────────────────────────┘ Kernel Space Device (e.g., serial port, NIC)

Stream Head

Topmost component. Interfaces with user-space. Handles read(), write(), ioctl() system calls. Converts between user and kernel data formats.

Modules

Middleware layers that transform data passing through. They can be pushed onto or popped off the stream at runtime. Examples: error correction, protocol processing.

Stream Driver

The bottommost component. Directly communicates with the hardware device. Like a regular device driver but STREAMS-compatible.

Message Queues

Data flows as messages, not raw bytes. Each component has a read queue and write queue. Enables flow control and priority messaging.

File Systems
How operating systems organize, store, and retrieve data on disk
Virtual File System (VFS)

VFS is an abstraction layer in the kernel that provides a uniform interface for all file system types. Applications call generic functions like open(), read(), write() — VFS routes them to the correct underlying file system (ext4, NTFS, FAT32, etc.).

Application │ open(), read(), write(), close() ▼ ┌─────────────────────────────────┐ │ Virtual File System (VFS) │ ← Uniform interface └──────┬──────────┬──────────┬───┘ ▼ ▼ ▼ ext4 NTFS FAT32 ← Concrete file systems │ │ │ └──────────┴──────────┘ │ Block Device Layer (disk driver)
Inodes — The Heart of UNIX File Systems

An inode (index node) stores all metadata about a file EXCEPT its name. The directory maps filename → inode number.

What an inode stores:

  • File type (regular, directory, symlink)
  • Permissions (rwxrwxrwx)
  • Owner (UID) and group (GID)
  • File size in bytes
  • Timestamps (created, modified, accessed)
  • Link count (hard links pointing to this inode)
  • Pointers to data blocks

What an inode does NOT store:

  • The filename (stored in the directory)
  • The actual file content (stored in data blocks)
Memory Hook
Directory = Phone book (name → number). Inode = the person (all their info). Data blocks = what they actually say.
File Allocation Methods

Contiguous

All blocks stored consecutively on disk. Fast sequential access. Suffers from external fragmentation. Hard to grow files.
[ A | A | A | B | B | _ | C | C | C ]

Linked

Each block has a pointer to the next. No external fragmentation. Poor random access. Unreliable if a pointer breaks.
[A1|→4] [A2|→7] [A3|→0] scattered blocks

Indexed (FAT)

An index block holds all data block pointers. Supports random access. Index block overhead. FAT32 uses a global file allocation table.
Index: [4][7][12] → actual data blocks

Extents (ext4/APFS)

Stores (start block, length) pairs instead of individual block pointers. Efficient for large files. Reduces fragmentation.
Extent: start=100, len=50 → 50 contiguous blocks
Journaling

Journaling records intended changes to a log (journal) before writing them to disk. If the system crashes mid-write, the journal is replayed on recovery — preventing corruption.

1
Write to journal (log)

Metadata (and optionally data) is written to the journal first

2
Commit

A commit record marks the journal entry as complete

3
Write to disk

Changes are written to their final location on disk

4
Clear journal

Journal entry is freed after successful write

Free Space Management

Bit Vector (Bitmap)

One bit per disk block. 0 = free, 1 = used. Fast to find contiguous free blocks. Requires extra space for the bitmap itself.

Linked Free List

Free blocks are linked together. No extra space needed (uses the free blocks themselves). Slow — must traverse the list to find contiguous space.
Exam Tips
ext2 = no journal (good for USB/flash). ext3 added journaling to ext2. ext4 added extents + multiblock allocation. NTFS uses $LogFile for journaling. FAT32 = no journal, 4GB file size limit.
Synchronization
Coordinating concurrent access to shared resources to prevent data corruption
The Problem: Race Conditions

A race condition occurs when two or more processes access and manipulate shared data concurrently, and the final result depends on the order of execution — which is unpredictable.

// Two threads both execute: counter++ // counter++ is actually 3 operations: LOAD R1, counter // read value ADD R1, #1 // increment STORE counter, R1 // write back // If two threads interleave → counter ends up as 1 instead of 2!
Critical Section Requirements

A critical section is a code segment that accesses shared resources. Any correct solution must satisfy ALL three:

1. Mutual Exclusion

Only ONE process can be inside the critical section at a time.

2. Progress

If no one is in the CS and someone wants in, a decision must be made in finite time (no endless deferral).

3. Bounded Waiting

There is a limit on how many times other processes enter the CS before a waiting process gets in (no starvation).
Mutex (Mutual Exclusion Lock)

The simplest synchronization tool. A mutex has two states: locked and unlocked. Only the thread that locked it can unlock it.

mutex.acquire() // lock — blocks if already locked // ← critical section → shared_data++ mutex.release() // unlock — wakes a waiting thread
Pitfall: Deadlock
If thread A holds mutex1 and waits for mutex2, while thread B holds mutex2 and waits for mutex1 → deadlock.
Semaphores

A semaphore is an integer variable accessed only via two atomic operations:

wait() — also called P() or down()

Decrements the value. If value < 0, the process blocks (goes to sleep). Conceptually: "try to acquire a resource."
wait(S): S = S - 1 if S < 0: block()

signal() — also called V() or up()

Increments the value. If there are blocked processes, wakes one. Conceptually: "release a resource."
signal(S): S = S + 1 if S <= 0: wakeup()
TypeInitial ValueUse Case
Binary Semaphore1Acts like a mutex — mutual exclusion
Counting SemaphoreN (pool size)Control access to N identical resources (e.g., 5 printers)
Signaling Semaphore0Force ordering — A does something, then signals B to proceed
Monitors

A high-level synchronization construct. A monitor is a class/module where:

  • Only one process can be executing inside the monitor at any time (mutual exclusion is automatic)
  • Condition variables allow processes to wait inside the monitor without holding the lock
  • wait() on a condition variable releases the monitor lock and suspends the process
  • signal() wakes exactly one waiting process on that condition variable
monitor BoundedBuffer: condition not_full, not_empty procedure insert(item): if buffer.full(): wait(not_full) buffer.add(item) signal(not_empty) procedure remove(): if buffer.empty(): wait(not_empty) item = buffer.get() signal(not_full) return item

Process Control Block (PCB)

The OS's complete record of a process. Every process has exactly one PCB. Saved/restored on every context switch.

  • Process ID (PID) — unique identifier
  • Process state — ready/running/waiting/etc.
  • Program counter — next instruction address
  • CPU registers — all register values saved here
  • Scheduling info — priority, time used
  • Memory info — page tables, base/limit registers
  • I/O status — open files, pending I/O
  • Accounting info — CPU time used, start time

Context Switch

When the CPU switches from one process to another:

1
Save state of current process into its PCB

Registers, program counter, stack pointer, memory mappings

2
Select next process

Scheduler picks the next process from the ready queue

3
Restore state of new process from its PCB

Load its registers, PC, memory context — resumes exactly where it left off

Key Point
Context switch time is pure overhead — no useful work is done during it. This is why too-small time quanta in Round Robin hurts performance.

Deadlocks, Starvation & Resource Allocation
When processes get permanently stuck waiting for each other
The 4 Coffman Conditions (ALL must hold for deadlock)
Memorize These
If even one condition is broken, deadlock CANNOT occur.

1. Mutual Exclusion

At least one resource must be non-shareable — only one process can use it at a time. (e.g., a printer)

2. Hold and Wait

A process holds at least one resource AND is waiting to acquire additional resources held by others.

3. No Preemption

Resources cannot be forcibly taken from a process — they must be voluntarily released.

4. Circular Wait

A set of processes {P0, P1, …, Pn} exists where P0 waits for P1, P1 waits for P2, …, Pn waits for P0.
Handling Deadlocks: 4 Strategies
StrategyHowCost
PreventionDesign the system so that at least one Coffman condition can NEVER hold (e.g., require processes request all resources at once → eliminates Hold & Wait)Low resource utilization, may be impractical
AvoidanceDynamically check if granting a request keeps the system in a safe state (Banker's Algorithm). Only grant if safe.Must know max resource needs in advance
Detection & RecoveryAllow deadlocks to occur. Periodically run detection (wait-for graph cycle check). When found, recover by killing processes or preempting resources.Recovery overhead; partial work lost
Ignore (Ostrich)Pretend deadlocks don't happen and just reboot. Used by most consumer OSes (Windows, Linux) because deadlocks are rare enough that prevention overhead isn't worth it.Inconvenience when it does happen
Prevention: Eliminating Each Condition
Condition to EliminateHow to Eliminate It
Mutual ExclusionMake resources shareable (only works for read-only resources like files opened for reading)
Hold and WaitRequire processes to request ALL resources before starting, or release all before requesting more
No PreemptionIf a process requests a resource that can't be allocated, preempt all its held resources (save state, restore later)
Circular WaitImpose total ordering on resource types; processes must request resources in increasing order only
Safe State vs Unsafe State

Safe State

A sequence exists where every process can eventually obtain its needed resources, execute, and release them — allowing the next process to proceed. A safe state guarantees deadlock-free execution.

Unsafe State

No such safe sequence exists. This doesn't mean deadlock IS happening, but deadlock CAN happen depending on future requests. Avoidance algorithms refuse requests that would lead here.
Safe State → Unsafe State → Deadlock (avoidance prevents crossing the Safe→Unsafe line)
Starvation vs Deadlock vs Livelock
TermDefinitionExample
DeadlockAll involved processes are permanently blocked, each waiting for another in a cycle. No progress possible.P1 holds R1, wants R2. P2 holds R2, wants R1.
StarvationA process is perpetually denied resources even though they become available — always losing to higher-priority processes.Low-priority job never runs because high-priority jobs keep arriving. Fix: aging (increase priority over time).
LivelockProcesses keep changing state in response to each other but make no useful progress. They're "active" but stuck.Two people in a hallway each step aside to let the other pass, then step the same way, repeat forever.
Classic Concurrency Problems
Foundational problems that model real-world synchronization challenges
🍝 Dining Philosophers Problem

Setup: 5 philosophers sit at a round table. There are 5 forks, one between each pair. To eat, a philosopher needs BOTH adjacent forks. They alternate between thinking and eating.

[P0] / \ fork4 fork0 / \ [P4] [P1] \ / fork3 fork1 \ / [P3]─fork2─[P2]
The Deadlock Scenario
If all 5 philosophers pick up their LEFT fork simultaneously, each holds one fork and waits for the right fork (held by their neighbor) → circular wait → deadlock.

Solutions:

Solution 1: Max N-1 Diners

Allow at most 4 philosophers at the table at once. At least one can always eat. Simple but wasteful.

Solution 2: Asymmetric

Odd philosophers pick left-then-right. Even philosophers pick right-then-left. Breaks circular wait.

Solution 3: Monitor/Waiter

A monitor or "waiter" semaphore grants permission to pick up BOTH forks atomically. Only pick up if both are available.
📦 Producer-Consumer Problem (Bounded Buffer)

Setup: Producers generate data and add to a shared buffer of size N. Consumers remove data. Producers must wait when buffer is full; consumers must wait when buffer is empty.

SemaphoreInitial ValuePurpose
mutex1Mutual exclusion for buffer access
emptyN (buffer size)Count of empty slots — producer waits on this
full0Count of filled slots — consumer waits on this

Producer:

wait(empty) // wait for a slot wait(mutex) // lock buffer add item to buffer signal(mutex) // unlock signal(full) // notify consumer

Consumer:

wait(full) // wait for an item wait(mutex) // lock buffer remove item from buffer signal(mutex) // unlock signal(empty) // notify producer
Order Matters!
Always wait on the counting semaphore (empty/full) BEFORE waiting on mutex. Reversing the order causes deadlock.
📖 Readers-Writers Problem

Setup: A shared database. Multiple readers can read simultaneously (no conflict). A writer needs exclusive access — no readers or other writers while writing.

Semaphore/VariableInitialPurpose
rw_mutex1Exclusive access for writers (and the first/last reader)
mutex1Protects the read_count variable
read_count0Number of readers currently reading

Reader:

wait(mutex) read_count++ if read_count == 1: wait(rw_mutex) // first reader blocks writers signal(mutex) // ← read data → wait(mutex) read_count-- if read_count == 0: signal(rw_mutex) // last reader releases signal(mutex)

Writer:

wait(rw_mutex) // exclusive access // ← write data → signal(rw_mutex) // release
Two Variants
1st problem: Readers have priority — writers may starve.
2nd problem: Writers have priority — readers may starve.
🏦 Banker's Algorithm

A deadlock avoidance algorithm. Before granting a resource request, the OS checks if the resulting state is safe. Named after a bank that only loans money if it can still satisfy all potential future withdrawals.

Key Data Structures (for n processes, m resource types):

StructureSizeMeaning
Available[m]mHow many of each resource are currently free
Max[n][m]n×mMaximum resources each process may ever need
Allocation[n][m]n×mResources currently allocated to each process
Need[n][m]n×mRemaining resources each process may still request: Need = Max − Allocation

Safety Algorithm (find a safe sequence):

Safety Check
Work = Available.copy() Finish = [False] * n repeat: find i where: Finish[i] == False AND Need[i] <= Work if found: Work += Allocation[i] // process finishes, releases resources Finish[i] = True else: break if all Finish[i] == True: → SAFE STATE ✓ else: → UNSAFE STATE ✗
Worked Example
3 processes (P0, P1, P2), 1 resource type. Available = 2.
Allocation: P0=1, P1=2, P2=0. Max: P0=3, P1=3, P2=2.
Need: P0=2, P1=1, P2=2.

Try P1: Need[P1]=1 ≤ Work=2 ✓ → Work = 2+2 = 4, Finish[P1]=true
Try P0: Need[P0]=2 ≤ Work=4 ✓ → Work = 4+1 = 5, Finish[P0]=true
Try P2: Need[P2]=2 ≤ Work=5 ✓ → Work = 5+0 = 5, Finish[P2]=true
All finished → Safe sequence: <P1, P0, P2> ✓
Resource Allocation Graph & Wait-For Graph
Visual tools to detect and analyze deadlocks
Resource Allocation Graph (RAG)

A directed graph with two types of nodes:

  • Process nodes: Circles (○) — represent processes
  • Resource nodes: Rectangles with dots (▣) — each dot = one instance

Two types of edges:

  • Request edge P→R: Process P is waiting for resource R
  • Assignment edge R→P: Resource R is held by process P
(P1) ──request──→ [R1•] ↓ assign (P2) ←─assign── [R2••] │ └──request──→ [R1•] ○ = Process [•] = Resource (dots = instances)
Deadlock Detection via RAG
ConditionDeadlock?
Cycle in RAG, single-instance resourcesYES — definitely deadlock
Cycle in RAG, multi-instance resourcesMAYBE — possible but not guaranteed
No cycle in RAGNO deadlock
Deadlock example: (P1)──→[R1]──→(P2)──→[R2]──→(P1) Cycle with single instances = DEADLOCK ✗ No deadlock example: (P1)──→[R1] [R1]──→(P2) No cycle → SAFE ✓
Wait-For Graph

A simplified version of the RAG — only processes, no resource nodes. Used when all resources have single instances.

  • An edge Pi → Pj means "Pi is waiting for Pj to release a resource"
  • A cycle in the wait-for graph = deadlock
  • The OS periodically runs a cycle-detection algorithm on this graph
RAG: Wait-For Graph: (P1)──→[R]──→(P2) → (P1)──→(P2) If P1 waits for R, and R is held by P2, then P1 is "waiting for" P2.
RAG vs Wait-For Summary
RAG: processes + resources, two edge types, works with multi-instance resources.
Wait-For: processes only, simpler, only valid for single-instance resources — cycle = deadlock.
Deadlock Recovery Options

Process Termination

Kill one or more processes in the deadlock cycle. Either abort all (safe but costly) or abort one at a time and re-check (more targeted).

Resource Preemption

Forcibly take a resource away from a process (roll back to a safe state). Must handle: which process to preempt, rollback, and starvation prevention.
I/O Operations
How the OS communicates with hardware devices
Three Methods of I/O

Polling (Busy Waiting)

CPU continuously checks the device status register in a loop until the device is ready. Simple but wastes CPU cycles. Good only for very fast devices.
while (device.status != READY) ; // spin

Interrupts

CPU starts I/O and continues other work. Device interrupts the CPU when done. CPU saves state, runs interrupt handler, resumes. Efficient for slow devices.
start_io() // do other work... // interrupt fires: handle_interrupt()

DMA (Direct Memory Access)

A DMA controller transfers data directly between device and memory without CPU involvement per byte. CPU only involved at start and end (interrupt). Best for bulk transfers.
setup_dma(src, dst, len) // CPU does other work // DMA interrupt when done

Maskable vs Non-Maskable
Maskable: Can be temporarily disabled (ignored) during critical code sections. Most device interrupts are maskable.
Non-maskable (NMI): Cannot be disabled. Used for critical hardware failures, memory errors.

Stream Cipher vs Block Cipher

Stream Cipher

Encrypts data one bit or byte at a time continuously. Good for real-time communication (phone calls, streaming). Example: RC4.

Block Cipher

Encrypts data in fixed-size chunks (e.g., 128-bit blocks). Each block is encrypted independently or with chaining. Example: AES (128/192/256-bit blocks).

Authentication Factors

Something You Know

A secret in your memory. Password, PIN, security question answer, passphrase.

Something You Have

A physical object. Smart card, hardware token, phone (SMS code), authenticator app.

Something You Are (Biometrics)

A physical trait. Fingerprint, face recognition, retinal scan, voice pattern.
Two-Factor Authentication (2FA)
Requires ANY two factors from DIFFERENT categories. Password + SMS code = 2FA. Password + security question = NOT 2FA (both are "something you know").
Defense in Depth

A layered security strategy where multiple independent controls protect a system. If one layer fails, others remain. Like an onion — attacker must break through multiple layers.

Layer 1: Physical security (locked server room) Layer 2: Network perimeter (firewall, IDS) Layer 3: Host-based (antivirus, host firewall) Layer 4: Application (input validation, auth) Layer 5: Data (encryption, access control) ↓ Data at the center
Hash Functions

A hash function takes input of any size and produces a fixed-size output (digest). Properties:

  • One-way: Cannot reverse a hash to get the original input
  • Deterministic: Same input always produces same output
  • Avalanche effect: Tiny change in input → completely different hash
  • Collision resistant: Extremely hard to find two inputs with the same hash

Examples: MD5 (broken, don't use), SHA-256 (secure), SHA-3. Uses: password storage, file integrity checks, digital signatures.

Unique Technologies by OS

Linux / UNIX

  • VFS — Virtual File System layer (abstracts all FS types)
  • /proc filesystem — virtual FS exposing kernel/process info as files
  • POSIX — standard API (fork, exec, signals, semaphores)
  • inode-based file systems
  • Everything is a file — devices, sockets, pipes all appear as files
  • GRUB — common Linux bootloader
  • systemd / init — PID 1, manages services

Windows

  • NTFS — MFT, journaling, ACLs, EFS encryption
  • Win32 API / WinAPI — common interface for system calls
  • Registry — hierarchical config database (unique to Windows)
  • Active Directory — centralized auth/policy management
  • NTLM / Kerberos — Windows authentication protocols
  • DLL (Dynamic Link Library) — Windows equivalent of .so files
  • NTFS Alternate Data Streams — hidden data attached to files

macOS

  • APFS — copy-on-write, snapshots, native encryption
  • Mach kernel — microkernel at the core (part of XNU kernel)
  • launchd — macOS init system (replaces both init and cron)
  • Gatekeeper — app signing/notarization enforcement
  • Keychain — secure credential storage system
  • Spotlight — system-wide search (indexing daemon)

General OS Concepts

  • FAT32 — universal compatibility; 4GB max file size
  • exFAT — FAT replacement for flash; no file size limit; no journaling
  • NFS — Network File System (UNIX/Linux network FS)
  • Swap partition — Linux's virtual memory overflow area on disk
  • Page file — Windows' equivalent of swap space
Quick OS Memory Tricks
NTFS = Windows. ext4 = Linux (modern). APFS = macOS. UFS = UNIX. FAT32 = anywhere (flash drives, cross-platform). exFAT = flash drives without 4GB limit. ext2 = USB drives on Linux (no journaling = less wear).
Mounting — The 3 Steps
How the OS makes a file system accessible in the directory tree
What is Mounting?

Mounting attaches an external file system (on a USB drive, partition, network share, etc.) to a directory in the existing file system tree — called the mount point. After mounting, the contents of the device appear at that directory path.

Before mounting: / ├── home/ ├── etc/ └── mnt/ ← empty mount point After: mount /dev/sdb1 /mnt / ├── home/ ├── etc/ └── mnt/ ← now shows USB drive contents ├── photos/ └── readme.txt
The 3 Steps of Mounting
1
Verify the device contains a valid file system

The OS reads and validates the device's superblock (or volume control block). It checks that the file system type is recognized, the magic number is correct, and the volume is not corrupted. This confirms there is actually a mountable file system on the device.

2
Create an entry in the OS mount table

The OS adds a record to its internal mount table linking the device to the chosen mount point. This entry records the device path, the mount point directory, the file system type, and mount options (read-only, permissions, etc.).

3
Attach the file system to the directory tree at the mount point

The mount point directory's inode is updated to point to the root of the newly mounted file system. All path lookups that reach the mount point are transparently redirected into the new file system. The device is now accessible.

Unmounting (Reverse)
Unmounting reverses this: flush all cached writes to disk, remove the mount table entry, and detach the file system from the directory tree. The mount point directory returns to its original (usually empty) state.
